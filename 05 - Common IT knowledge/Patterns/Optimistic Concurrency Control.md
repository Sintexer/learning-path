**Definition:** Optimistic Concurrency Control (OCC) is a strategy for handling concurrent updates _without acquiring locks upfront_. It assumes conflicts are rare, lets operations proceed freely, and instead checks — at the moment of writing — whether the data is still in the state you expect. If not, you reject or skip the operation rather than corrupt something.

**Contrast with pessimistic locking:** [[Pessimistic Locking]] (e.g., SQL `SELECT ... FOR UPDATE`) acquires a lock _before_ you even read the data, blocking any other transaction from touching it until you're done. Safe, but expensive — reduces concurrency, holds resources, and can cause deadlocks under load. OCC is the "ask forgiveness, not permission" model, better suited for high-throughput systems like event streams where locking every consumer against every other would defeat the purpose entirely.

**Two flavors of OCC you should be able to distinguish:**

1. **[[Compare-And-Swap]] / expected-version style** — "Apply this change _only if_ the current version exactly equals X (the version I expected when I computed this change)." This is strict — any mismatch, even from a gap, causes rejection. Common in systems needing exact causal chains (e.g., "apply this diff only if nothing else changed since I last read").
2. **Monotonic version-stamp style** ([[Version Guard]]) — "Apply this change if its version is _strictly greater than_ what I currently have." More lenient — tolerates gaps (e.g., missing sequence 46 doesn't block 47 or 48 from applying), which is usually what you want for **read models built from event streams**, since perfect gapless delivery isn't always realistic (compaction, selective replay, etc.). This is the version most relevant to [[Kafka Consumer]] replay-safety.

**Where does the version number come from?** It must be assigned by a **single authoritative source** per entity — usually whichever service owns the write-side truth for that entity (the feed provider owning match odds, or your core Bets service owning bet state). Never let multiple independent producers assign versions to the same entity's version counter — that reintroduces exactly the race-condition problem we're trying to avoid.
