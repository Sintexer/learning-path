**Monotonic version-stamp style** — "Apply this change if its version is _strictly greater than_ what I currently have." More lenient — tolerates gaps (e.g., missing sequence 46 doesn't block 47 or 48 from applying), which is usually what you want for **read models built from event streams**, since perfect gapless delivery isn't always realistic (compaction, selective replay, etc.). This is the version most relevant to Kafka consumer replay-safety.

Highly related to [[Kafka Consumer]].

Suppose you use a plain **timestamp** as your version field instead of a monotonically incrementing integer. What's a real risk with that choice, specifically in a distributed system with multiple producers?

> Timestamps might overlap. But there is a bigger problem. If Producer A and Producer B run on different servers, their system clocks are never perfectly synchronized (NTP sync error is normal, usually milliseconds, sometimes more). So imagine Producer A generates event X at "true" time T, and Producer B generates event Y at "true" time T+1 (genuinely, causally later). But because Producer B's clock is running 5ms behind, event Y gets timestamped as _earlier_ than event X. Your version guard now thinks Y is stale and incorrectly discards a legitimately newer update. **A monotonically incrementing counter, maintained by a single authoritative source (usually the write-side database), doesn't have this problem** — it has no relationship to wall-clock time at all, so there's no skew to worry about. This is why real systems almost always prefer sequence numbers/logical versions over timestamps for this exact purpose.
