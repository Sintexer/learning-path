**Eventual consistency** is a property of a distributed system that guarantees that, if no new updates are made, all replicas will eventually return the same value. While **[[Replication Lag|asynchronous replication lag]]** (the time it takes for data to physically travel from a primary node to secondary nodes over a network) is a primary driver, several other architectural factors and mechanisms cause eventual consistency:
1. **Multi-Leader and Leaderless Architectures (Concurrent Writes)**: [[Active-active systems]] or [[Leaderless Replication]].  Not due data latency or lag, but because the system is resolving _mathematical and logical divergence_.
2. **Caching Layers (Application Level)**: Time-to-Live (TTL) Caches, Cache-aside invalidation delays and Cache-aside invalidation delays: If the message to invalidate or update the cache is dropped, delayed, or processed asynchronously via an event bus, clients reading from the cache experience eventual consistency.
3. **Asynchronous Messaging and Event-Driven Architectures**
4. **Network Partitions and Node Failures** ([[CAP Theorem]])
5. **Gossip Protocols**. In fully decentralized or peer-to-peer systems: Nodes do not have a central coordinator to stream changes to. Instead, they randomly "gossip" with a few neighbors periodically to share state. It takes multiple rounds of probabilistic communication for a state change to permeate the entire cluster. This is an architectural choice that causes eventual consistency by design, independent of simple network pipe latency.
6. **Read Repair and Anti-Entropy Processes**: [[Read Repair]] and [[Anti-Entropy]]
7. **Disconnected or Offline-First Clients**: A mobile app may write data locally while on an airplane or in a subway with no internet. The system is fundamentally eventually consistent, and the "lag" here is dictated by user behavior (when they reconnect to Wi-Fi) rather than database replication internals.
